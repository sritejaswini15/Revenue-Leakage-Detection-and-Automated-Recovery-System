# Deployment (Render)

`render.yaml` is a Render Blueprint that creates:

| Resource | Type | Notes |
|---|---|---|
| `recoverx-postgres` | PostgreSQL | System of record |
| `recoverx-api` | Web service (Docker, `backend/`) | Runs `alembic upgrade head`, then Uvicorn; health check `/health` |
| `recoverx-frontend` | Web service (Docker, `frontend/`) | Next.js standalone server; proxies `/api/*` to the API |
| `recoverx-cleanup` | Cron job, hourly | Expires stale payment links, closes unpaid cases past `case_expiry_days`, then sends due reminders, escalations and promise checks (`scripts.run_due_workflows`). Shares the API's settings, including `CREDENTIALS_ENCRYPTION_KEY`, through `fromService` |

## First deployment

1. **Create the Blueprint.** In the Render dashboard, choose *New → Blueprint* and select this repository. Render reads `render.yaml`.
2. **Enter the secrets** marked `sync: false` (see [ENVIRONMENT.md](ENVIRONMENT.md)):
   - `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` (16+ characters): the first administrator.
   - `RAZORPAY_WEBHOOK_SECRET`: the secret you set on the Razorpay webhook (step 5).
   - `BOOTSTRAP_RAZORPAY_ACCOUNT_ID`: your Razorpay account id (`acc_…`), used to route webhooks.
   - `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET`: only for the legacy single-merchant setup. Merchants can instead store their own keys in the app (step 6).

   `AUTH_SECRET` and `CREDENTIALS_ENCRYPTION_KEY` are generated by Render. **Never regenerate `CREDENTIALS_ENCRYPTION_KEY`** once merchants have stored keys: they could no longer be decrypted. `ALLOW_LIVE_PAYMENTS` is `false`, so only `rzp_test_` keys are accepted.
3. **Wire the two URLs.** Render assigns `https://<service>.onrender.com` addresses. If yours differ from the defaults in `render.yaml`, update them:
   - `recoverx-api` → `CORS_ORIGINS` = the frontend URL.
   - `recoverx-frontend` → `NEXT_PUBLIC_API_URL` = the API URL. The web server proxies `/api/*` there, so the browser only talks to the frontend's own origin and the HttpOnly session cookie stays first-party. Next.js compiles the proxy target into the build (Render passes service environment variables to Docker builds as build arguments), so **redeploy the frontend** after changing it.
4. **Deploy.** The API refuses to start if a production secret is missing or still a development default. The error names the variable.
5. **Point Razorpay at RecoverX.** In the Razorpay Dashboard (test mode first), go to *Settings → Webhooks → Add*:
   - URL: `https://<api>/webhooks/razorpay`
   - Secret: the same value as `RAZORPAY_WEBHOOK_SECRET`
   - Events: `payment.failed`, `payment.authorized`, `payment.captured`, `payment_link.paid`, `payment_link.partially_paid`, `payment_link.expired`, `payment_link.cancelled`, `invoice.paid`, `invoice.partially_paid`, `invoice.expired`, `subscription.pending`, `subscription.halted`, `subscription.charged`. Each is handled as described in [API.md](API.md#razorpay-webhooks); an event RecoverX can't use is acknowledged and stored, never retried
6. **Optional: per-merchant keys.** Sign in as an administrator, open **Integrations → Razorpay credentials**, and save the merchant's `rzp_test_` key id and secret, Razorpay account id and webhook secret with *Verify with Razorpay* ticked. Each merchant's webhooks are then verified with its own secret, and its recovery actions use its own keys.

## Verify

```bash
curl https://<api>/health                     # {"status":"ok",...}
```

Then sign in to the frontend with the bootstrap administrator. **Integrations** shows which providers are live, and **Simulator** exercises the full pipeline without real money. Check that the session cookie is set (browser devtools → Application → Cookies: `recoverx_session`, HttpOnly, Secure).

## Razorpay test mode

Prove the integration with your test keys before anything else. From `backend/`, in your own shell (never paste keys into chat, tickets or commits):

```bash
RAZORPAY_KEY_ID=rzp_test_… RAZORPAY_KEY_SECRET=… python -m scripts.razorpay_test_roundtrip
RAZORPAY_KEY_ID=rzp_test_… RAZORPAY_KEY_SECRET=… python -m scripts.razorpay_test_roundtrip --keep-link
```

The first command authenticates, creates a ₹1 Payment Link exactly as RecoverX does, reads it back and cancels it. It refuses `rzp_live_` keys and never prints secrets. The second leaves the link open and prints the manual steps: pay it with a Razorpay test method (for example UPI `success@razorpay`), and confirm the `payment_link.paid` webhook reaches `/webhooks/razorpay` and the case becomes `RECOVERED`.

Then either store the keys per merchant under **Integrations**, or (single merchant) set `PAYMENT_PROVIDER=razorpay`, `RAZORPAY_KEY_ID=rzp_test_…` and `RAZORPAY_KEY_SECRET` on the API and the cron job and redeploy. Recovery actions then create real Razorpay Payment Links (amounts in paise, expiring after `PAYMENT_LINK_TTL_HOURS`), and expired cases cancel theirs. Live keys stay refused while `ALLOW_LIVE_PAYMENTS=false`; changing that is a business decision that needs explicit authorization after a complete test-mode run.

## Operations

- **Migrations.** These apply automatically on every API start and are idempotent. Roll forward with a new revision rather than editing old ones.
- **Rotating the admin password.** Change `BOOTSTRAP_ADMIN_PASSWORD` and redeploy. Only that account is touched. Other users change their own password under **Account**; administrators reset others' under **Users**.
- **Rotating Razorpay keys.** Save new keys under **Integrations** (the webhook secret is kept unless you enter a new one). Every change is audited without the secret.
- **Demo data.** Production starts empty (`SEED_DEMO_DATA=false`). Setting it to `true` seeds the demo merchant on an empty database and enables `/demo/reset`, which **replaces all business data**. Demo logins are never created in production.
- **Logs.** In production every process (API, hourly job, Temporal worker) writes one JSON object per line to stdout (`LOG_FORMAT=json`), each carrying the `request_id` that is also returned in `X-Request-ID`, so a support report can be matched to its log lines. Customer payment tokens are redacted and customers are logged by internal id, never by email or phone. View them in the service's *Logs* tab; set `LOG_LEVEL=DEBUG` temporarily for more detail.
- **Errors.** Set `SENTRY_DSN` on the API (the hourly job reads the same value) to report unhandled errors. Request bodies, local variables and personal data are not sent.
- **Scaling.** The API is stateless: sessions and the login rate limiter live in PostgreSQL, so every instance enforces the same limits. Add instances in the dashboard.
- **Case expiry.** Unpaid cases close after `case_expiry_days` (Policies; default 7) in the hourly job. To run it immediately on a demo deployment, an administrator can call `POST /demo/run-due-workflows`.
- **Plans.** The Blueprint uses Render's `0.5c-512mb` instance type for the services and cron job and `0.1c-256mb` for PostgreSQL (the smallest paid tiers); change them to suit your account.

## Durable workflows (optional)

Render doesn't host Temporal. To use durable multi-day workflows, provision Temporal Cloud or a self-hosted cluster. Then:

1. Set `TEMPORAL_ENABLED=true`, `TEMPORAL_HOST` (e.g. `<namespace>.<account>.tmprl.cloud:7233`), `TEMPORAL_NAMESPACE` and `TEMPORAL_API_KEY` on the API. With an API key the client connects over TLS. The hourly job reads `TEMPORAL_ENABLED` from the API, and with it on only expires cases, so follow-ups are never sent twice.
2. Add a Background Worker service with `rootDir: backend` and the command `python -m app.infrastructure.temporal.worker`. It needs the API's environment: `DATABASE_URL`, `CREDENTIALS_ENCRYPTION_KEY`, `AUTH_SECRET`, the `TEMPORAL_*` values and any `RAZORPAY_*` keys, because its activities send reminders and check payments through the same Tool Gateway.

Temporal integration has been exercised in this repository only through its in-process fallback and code paths that don't need a server; run a test case through a real Temporal namespace before relying on it.

Without Temporal, the hourly `recoverx-cleanup` job advances follow-ups and promise checks, so reminders go out within an hour of falling due.

## Recovery advisor (optional)

By default the advisor is RecoverX's deterministic rules and needs nothing. To let Claude recommend, set `LLM_PROVIDER=anthropic` and the secret `ANTHROPIC_API_KEY` on the API (and on the Temporal worker if you run one). The key stays on the server; the frontend never sees it. Each new case then makes one Claude request while its webhook is processed, so keep `LLM_EFFORT=low` and `LLM_TIMEOUT_SECONDS` short, and note that `POST /demo/run-batch` makes one request per case. Integrations shows *Claude* once the key is set. See [AI.md](AI.md).

## What needs real credentials or infrastructure

| Integration | Default in this Blueprint | To make it real |
|---|---|---|
| Razorpay | Simulated provider | Merchant `rzp_test_` keys under Integrations, or `PAYMENT_PROVIDER=razorpay` with test keys; run `scripts.razorpay_test_roundtrip` first. Not yet verified against a real Razorpay account in this repository |
| Razorpay webhooks | Verified with HMAC | The webhook configured in the Razorpay dashboard with `RAZORPAY_WEBHOOK_SECRET` |
| WhatsApp, email | Simulated: messages are stored, not sent | Implement `MessagingProvider` for a real provider (no adapter exists yet) |
| Temporal | Off; the hourly job advances follow-ups | Temporal Cloud plus a worker service (above) |
| Claude advisor | Off; rules decide | `ANTHROPIC_API_KEY`; never called live in this repository's verification |
| Sentry | Off | `SENTRY_DSN` |

## Production checklist

- [ ] `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` (16+), `RAZORPAY_WEBHOOK_SECRET`, `BOOTSTRAP_RAZORPAY_ACCOUNT_ID` entered; the API starts (it refuses missing or development values).
- [ ] `CORS_ORIGINS` is the frontend URL and the frontend's `NEXT_PUBLIC_API_URL` is the API URL; frontend redeployed after changing it.
- [ ] `curl https://<api>/health` returns `ok`; signing in sets a Secure, HttpOnly `recoverx_session` cookie.
- [ ] Integrations shows Razorpay, webhooks, messaging, Temporal and the advisor exactly as intended: simulated where you expect simulated.
- [ ] Razorpay test-mode round trip done and a test `payment_link.paid` webhook recovered a case.
- [ ] `SEED_DEMO_DATA=false` and `ALLOW_LIVE_PAYMENTS=false` unless deliberately changed.
- [ ] `CREDENTIALS_ENCRYPTION_KEY` is backed up somewhere safe; losing it makes stored merchant keys unreadable.

## Other container platforms

Both images are platform-neutral: the API reads `PORT` and runs migrations on start, and the frontend reads `PORT` and binds `0.0.0.0`. On Railway or Fly.io, deploy `backend/` and `frontend/` as separate services, attach PostgreSQL as `DATABASE_URL`, pass `API_URL` (the API's address as the frontend server can reach it) as a build argument for the frontend, and set the same variables as above. `docker compose up --build` runs the whole stack locally; there the frontend proxies to `http://backend:8000`.
